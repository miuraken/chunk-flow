# スパイク S3: デコード速度と、解析・再生の時間軸の一致（audio-analysis）

- 担当: audio-analysis / ブランチ: `agent/audio-analysis/s3-spike`（main 563c695 から）
- 実施日: 2026-10-14
- 端末: **エミュレータ Pixel_8_Pro（android-36、arm64、`sdk_gphone64_arm64`）だけ**。Pixel 実機での計測は **実機待ち**。
- 対象の節: §3（解析性能・メモリ・時刻精度）、§7.3.1、§11（S3）、§12（時刻のずれのリスク）

> [!IMPORTANT]
> **速度の数値はすべてエミュレータの参考値**です。エミュレータは playback と共用で、ホスト（Mac）は計測中にメモリ不足
> （スワップ 13GB 使用）になり、同じ計測でも時間帯で 4〜5 倍変わりました。**目標（30 分を 60 秒以内）を満たすかどうかは未確認**で、
> 実機での計測が必要です。一方、**時間軸（クリックの時刻）とメモリの結果は、負荷に左右されない**（サンプル数とヒープ量の計測）ので、
> エミュレータの結果として扱えます（ただし端末のデコーダが違えば変わり得るので、実機で再確認する）。

## 1. まとめ（結論と提案）

| 項目 | 結果 | 目標 | 判定 |
| --- | --- | --- | --- |
| 30 分のデコード + 解析の時間 | エミュレータで 78〜89 秒（同期モード、負荷の軽い時間帯）。負荷の重い時間帯は 190〜383 秒。非同期モードは同期の約 1.3〜1.8 倍速い（実教材の 30 分の MP3 で 190〜200 秒 vs 299〜301 秒） | 60 秒以内（Pixel 8 クラス） | **実機待ち** |
| 追加のヒープ（30 分・60 分、実教材を含む） | Java ヒープ +8〜16MB、ネイティブ +4〜8MB、PSS +8〜23MB（60 分でも Java +13MB） | 64MB 未満 | 満たす（エミュレータ） |
| 解析（モノラル化 → 16kHz → ビン・特徴量）の時間 | 30 分で 3.5〜4.1 秒（全体の約 5%） | — | ボトルネックはデコーダ |
| 解析と ExoPlayer の時間軸のずれ | **MediaExtractorCompat + 出力サンプル数の累計**なら全形式で 0.1ms 未満。**MediaExtractor（プラットフォーム）だと MP3 で 12ms（44.1kHz）/ 24ms（22.05kHz）ずれる** | 20ms 未満 | Compat なら満たす |
| 30 分・60 分での時刻のドリフト | なし（最初と最後のクリックのずれが同じ） | — | 満たす |
| ExoPlayer と ffmpeg（PC ツール）の時間軸のずれ | MP3 だけ **ExoPlayer が 529 サンプル早い**（44.1kHz で -12.0ms、22.05kHz で -24.0ms）。他の形式は 0ms | 文字起こしと再生位置 50ms 未満 | 満たすが、22.05kHz の MP3 は補正したい |

**設計への提案**（判断は lead に任せます）

1. **抽出器は `MediaExtractorCompat`（media3-inspector）を使う**（§7.3.1 の選択）。ExoPlayer と同じ Media3 の抽出器なので、
   エンコーダ遅延の扱いが ExoPlayer と同じになり、出力サンプル数の累計から求めた時刻が再生位置と一致した（全形式で 0.1ms 未満）。
   プラットフォームの `MediaExtractor` は MP3 のエンコーダ遅延を 576 として MediaCodec に渡すため、ExoPlayer（1105）と 529 サンプルずれる。
2. **時刻は出力サンプル数の累計から求め、自前ではトリミングしない**。`MediaExtractorCompat` の形式（`encoder-delay` / `encoder-padding` を含む）を
   そのまま `MediaCodec.configure()` に渡すと、Codec2 のデコーダ自身が先頭と末尾を削る（m4a・MP3 で確認）。
   **PTS（`presentationTimeUs`）から求める方法は使わない**（形式・抽出器によって 6〜55ms ずれた）。
3. **MediaCodec は非同期モード（`setCallback`）を検討する**（§7.3.1 は同期モードと書いている）。エミュレータでは同期モードより 1.3〜1.8 倍速く、
   ExoPlayer（API 31 以上は非同期モード）と同程度だった。ただし非同期モードで 1 回だけ出力が 1008 フレーム欠けた（§4.4、原因は未確認）ので、
   採用するなら「出力フレーム数と長さの整合の検査」を入れる。実機で同期 / 非同期を比べてから決めたい。
4. **文字起こし（ffmpeg の時間軸）を MP3 で取り込むときは、−529 サンプル（= −529 / サンプルレート 秒）の補正を既定で入れる**（§7.4.6 の補正の既定値）。
   Media3 は MP3 のエンコーダ遅延を「LAME の遅延 + デコーダ遅延 529」として削るが、`c2.android.mp3.decoder` はデコーダ遅延を出力しないため、
   529 サンプル削りすぎる（と解釈できる結果。Media3 側の既知の問題かは未確認）。LAME ヘッダのない MP3 でも同じ 529 サンプルの差だった。
   形式 v1（§7.4.3「ffmpeg と ExoPlayer の既定の扱いに合わせる」）では両者が一致する前提だが、MP3 では一致しない。
   なお、端末のデコーダが変われば差も変わり得るので、実機で同じ計測をして確かめる。
5. **`MediaExtractorCompat` で FLAC を読むと、最後のサンプルが繰り返し返され EOS にならない**（`advance()` が true を返し続ける）。
   本実装では「時刻が進まないサンプルが続いたら終わり」とする対策が必要（スパイクでは 8 回で打ち切り）。Media3 の不具合として報告済みかは未確認。
6. **解析は前面で開始したフォアグラウンドサービスの中で動かす**（§7.3.4 のとおり）。エミュレータで計測アプリが背面に回ると、
   キャッシュされたアプリとして凍結され、計測が止まった（30 分の ADTS のデコードが 722 秒）。

## 3. 測り方

### 3.1 デコード + 解析（計測 1・2）

- 抽出器（`MediaExtractor` または `MediaExtractorCompat`）→ `MediaCodec`（同期モード。入力は待たずに入るだけ入れ、入れられないときだけ出力を 5ms 待つ）
  → `AnalysisPipeline`（モノラル化 → 16kHz → 10ms のビンと特徴量）。PCM 全体は保持しない。
- 時間: 壁時計、計測スレッドの CPU 時間、パイプラインにかかった時間。デコードは別プロセス（`media.swcodec`）で行われるため、
  計測スレッドの CPU 時間にはデコードの CPU は入らない。
- メモリ: 開始前に GC して基準値を取り、20ms ごとに Java ヒープ（`totalMemory - freeMemory`）とネイティブヒープ、500ms ごとに PSS の最大値を記録する。
- クリックの時刻（ネイティブのレートで検出し、16kHz の出力でも検出する）:
  - **累計**: 出力したサンプル数の累計 / レート
  - **累計 − 遅延**: 形式の `encoder-delay` をさらに自前で引いたもの
  - **PTS**: 出力バッファの `presentationTimeUs` + バッファ内の位置
  - **16kHz 累計**: リサンプル後のサンプル数の累計 / 16000（本実装で使う時間軸）

### 3.2 ExoPlayer の再生位置（計測 3）

- `DefaultRenderersFactory.buildAudioSink` を上書きし、`DefaultAudioSink` の最終段（`AudioOutput`、Media3 1.11 の `setAudioOutputProvider`）を差し替える。
  AudioTrack に書く直前の PCM（ギャップレスのトリミングの後）でクリックを検出し、その位置を「フラッシュ後に書いたフレーム数」k とする。
- `DefaultAudioSink` は「再生位置 = オフセット + 出力の再生位置」で位置を求めるので、`handleBuffer` のたびに
  `getCurrentPositionUs() − output.getPositionUs() − レンダラーのオフセット（1e12 µs）` を記録し、
  クリックの再生位置 = オフセット + k / レート とした（ExoPlayer 自身の対応付けをそのまま使う）。オフセットは全ファイルで常に 0 だった。
- 高速モード: 出力は AudioTrack に書かず、書いた分をすぐ「再生済み」とする（等速より速く進むので 30 分・60 分の全体を測れる）。
  端末の出力遅延（AudioTrack のレイテンシ）は含まない。等速モード（本物の AudioTrack）も用意したが、今回は使っていない。

### 3.3 ffmpeg（PC ツールの時間軸）

`s3_audio.py ffmpeg-clicks` で、ffmpeg 8.0.1 でモノラルにデコード（ネイティブのレートと `-ar 16000`）し、各正解の ±0.3 秒で最初に閾値（0.3）を超えたサンプルの時刻を求める。

- 16kHz 累計（本実装の時間軸）は、ネイティブの累計との差が 0.04ms 以内（リサンプラの位相のずれなし）。
- **Compat 累計と ExoPlayer の差は全形式で 0.01ms 以下**。Platform 累計と ExoPlayer の差は MP3（LAME あり）で 12ms / 24ms。
- 「累計 − 遅延」（自前でトリミング）はすべて削りすぎになった（m4a −23.22、MP3 −13.06 / −37.05 など）。**Codec2 のデコーダは、
  `MediaFormat` の `encoder-delay` / `encoder-padding` を見て自分で削る**（例: Platform の MP3 は 60 秒ちょうどの 2,646,000 フレームを出力）。
- 解釈: `c2.android.mp3.decoder` はデコーダ遅延（529 サンプル）を出力しない。ヘッダのない MP3 で ffmpeg は +25.06ms（576 + 529 = 1105 サンプル）、
  Codec2 は +13.06ms（576 サンプル）。Media3 は LAME の遅延 576 に 529 を足した 1105 を削るので、Codec2 では 529 サンプル削りすぎる。
- 30min / 60min: 30 分の MP3 VBR（ExoPlayer −11.995、Compat 非同期 −12.00）、30 分の 22.05kHz MP3（−23.99 / −24.00）、
  30 分の AAC m4a / ADTS（Platform / Compat とも 1min と同じ）、ffmpeg の 30 分・60 分（全形式で 1min と同じ）で、
  **最初と最後のクリックのずれは同じ（ドリフトなし）**。60 分の MP3 VBR（ExoPlayer、Compat 非同期）と 30 分の Opus も同じ（§4.5）。

### 4.2 文字起こしの時刻とのずれの見込み（S1 と合同）

PC ツール（ffmpeg でデコード）の時刻と ExoPlayer の再生位置の差（= ExoPlayer − ffmpeg）:

| 形式 | 差 | 備考 |
| --- | --- | --- |
| MP3（LAME あり / なし、44.1kHz） | **−12.0ms** | 529 / 44100。48kHz なら −11.0ms |
| MP3（22.05kHz） | **−24.0ms** | 529 / 22050。16kHz の MP3 なら −33.1ms（計測していない、計算値） |
| AAC m4a、Opus、Vorbis、FLAC、WAV | 0ms | |
| AAC ADTS | 0ms | 両方ともトリミングしない（どちらも正解より +23.22ms） |

- ffmpeg の `-ar 16000`（Whisper の入力）は、ネイティブのレートとの差が 0.03ms 以内。S1 は 16kHz で読んでも時刻は変わらない。
- 文字起こし自体の時刻の粗さ（Whisper のタイムスタンプ）はここに含まない（S1 の範囲）。
- §3 の目標（文字起こしと再生位置 50ms 未満）に対して、デコードの違いによる分は最大 24ms（22.05kHz の MP3）。
  補正（提案 4）を入れれば 0ms にできる。

### 4.4 気づいた問題

1. **MediaExtractorCompat + FLAC で EOS にならない**: 最後のサンプル（時刻 59.977 秒）が繰り返し返され、`advance()` も true のまま。
   打ち切らないと無限に続く（対策後も 8 サンプル分の 0.18 秒が余分に出力された）。プラットフォームの抽出器と ExoPlayer の再生では起きない。
2. **非同期モードで 1 回だけ出力が欠けた**: 1 分の AAC m4a（Platform、非同期）で、出力が 2,644,992 フレーム（正しくは 2,646,000）になり、
   3 個目以降のクリックが −23.2ms ずれた。同じ条件の他の 5 回は正常。原因は未確認（スパイクのコードの不具合の可能性もある）。
3. **プロセスの凍結**: 計測アプリが背面に回ると凍結されて計測が止まった（前面に戻るまで進まない）。`MeasureService`（mediaProcessing のフォアグラウンドサービス）で回避。
4. ExoPlayer の高速モードで WAV（1 分）が 127 秒かかった（他の形式は数秒）。クリックの時刻は正しい。プローブ側の問題か未確認。

## 5. 実機待ちの項目と手順

実機（Pixel 8 クラス）がつながったら、次の手順で計測する（所要 1 時間程度）。

```sh
# 1. 音源を生成（未生成なら）
python3 spikes/audio/scripts/s3_audio.py generate --minutes 30 --out spikes/audio/build/testaudio/30min
python3 spikes/audio/scripts/s3_audio.py generate --minutes 1 --period 5 --out spikes/audio/build/testaudio/1min
# 2. ビルドとインストール、音源の転送
./gradlew :spikes:audio:assembleDebug
adb install -r spikes/audio/build/outputs/apk/debug/audio-debug.apk
D=/sdcard/Android/data/com.miuraken.chunkflow.spike.audio/files/s3
adb shell mkdir -p $D && adb push spikes/audio/build/testaudio/1min spikes/audio/build/testaudio/30min $D/
# 3. 計測（画面のボタンでも実行できる。端末は充電中・画面オン・他のアプリを閉じた状態で）
A="adb shell am start -a com.miuraken.chunkflow.spike.audio.RUN --activity-single-top -n com.miuraken.chunkflow.spike.audio/.SpikeActivity"
$A --es cmd suite --es path 1min                       # 時間軸（全形式・3 方式）
$A --es cmd speed --es path 30min/mp3_cbr128.mp3 --ei repeat 2
$A --es cmd speed --es path 30min/aac_lc128.m4a --ei repeat 2
$A --es cmd speed --es path 30min/opus64.opus
# 4. 結果の取得と集計
adb pull /sdcard/Android/data/com.miuraken.chunkflow.spike.audio/files/s3_results.jsonl .
python3 spikes/audio/scripts/s3_summarize.py s3_results.jsonl
```

実機で確かめること: (1) 30 分のデコード + 解析が 60 秒以内か（同期 / 非同期、Platform / Compat）、(2) MP3 の 529 サンプルの差が実機のデコーダでも同じか、
(3) 非同期モードの出力の欠け（§4.4 の 2）が再現するか、(4) Compat + FLAC の EOS の問題が実機でも起きるか、(5) 実際の教材（30 分の MP3）での時間とメモリ。
