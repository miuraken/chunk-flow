## 1. 結論（要点）

1. **日韓（Pimsleur 日本語版、30.8 分）はほぼ問題なく動いた。** 候補チャンク 640 件のうち、2 つのモデルの
   判定が食い違ったのは 6〜8 件だけだった。明らかな誤りは turbo で 3 件、large-v3 で 2 件。
2. **英語-ヒンディー語（Pimsleur、30.6 分）は大きな問題がある。** ヒンディー語の短い語（数詞、「मेरे लिए」など）を
   `en` と判定し（確率 0.9〜1.0 のことも多い）、ローマ字で書いた。turbo では `en` と判定したチャンク 341 件のうち
   約 80 件、large-v3 では約 75 件がこれにあたる。英単語に聞き間違えた例（「बीस」→「Peace」「Beasts」、
   「तीस」→「These」）もある。このうち turbo の 83 件をヒンディー語を指定して認識し直すと、73 件がデーヴァナーガリーで
   書けた（§4.3）。
3. **平滑化は実際の教材でも害の方が大きい。** 解説と学習言語が交互に並ぶため、前後のチャンクがもう一方の
   言語であることが多い。ヒンディー語では、平滑化で言語が変わったチャンクの大半が誤った方向（`hi` → `en`）だった
   （turbo 13 件中 9 件、large-v3 26 件中 15 件が `en` への変更）。§6 で、対象を短いチャンクに限る提案をする。
4. **large-v3 は、ヒンディー語の言語判定の確率が turbo より低い**（文で 0.5〜0.7。turbo は 0.8〜0.97）。そのため
   平滑化で `en` に引かれ、`en` で認識してローマ字で書く誤りが増えた。短い語（「मेरे लिए」「चाहिए」「कुछ」）は
   large-v3 の方が正しい。どちらのモデルが良いかは、レビューの結果で決める必要がある。
5. 中国語の教材（52 秒）は中国語だけの会話で、日本語は含まれていなかった（言語ペアの推定 ja-zh は誤り）。
   20 チャンクがすべて `zh`（確率 1.00）になった。turbo のテキストには繁体字が混ざり（20 件中 3 件。large-v3 は 1 件。「問題在於…」など）、
   OpenCC で揃える必要があることを実際に確かめた。
6. 処理時間（RTF）は 0.44〜0.87 だった（M3 Pro）。学習者が答えるための 3〜4 秒の無音を VAD で飛ばすので、
   合成音声（0.8〜1.2）より短い。30 分の教材は turbo で 13.5〜16.6 分、large-v3 で 16.3〜20.4 分かかった。
7. 実際の教材で分かった 2 つの不具合を直した（コミット `47a31da`）。直した後の版で 3 本を処理し直してはいない
   （効果は記録から確認した件数だけ）。
   - 日本語・韓国語・中国語の文にラテン文字が混ざると、文字体系が合わないと判定していた（「Tシャツ」など）。
   - 平滑化で判定できなくなったチャンクを、前後に引かれた言語で認識していた（韓国語の発話をカタカナで書いた）。

## 4. テキストから分かった誤り（人間の確認の前に数えられるもの）

### 4.1 日韓（korean）

| 種類 | turbo | large-v3 | 例（抜粋） |
| --- | --- | --- | --- |
| 韓国語の発話を日本語（カタカナ）で書いた | 1 | 0 | 「길어요」→「キロヨ」（判定は ko 0.80 → 平滑化で null → ja で認識） |
| ラテン文字による文字体系の不一致（誤検出） | 2 | 2 | 「Tシャツ」「T」→ null。large-v3 では、ko で認識し直した「티샷」を採用した（誤り） |
| ナレーターの日本語の短い語を韓国語と判定 | 0 | 0〜1 | 「わ」「以前」（0.4〜0.5 秒）。どちらが正しいかは聞いて確かめる必要がある |
| 幻覚 | 0 | 0 | |

- 1 秒未満のチャンクが 51% ある。Pimsleur は単語を後ろから音節に分けて練習させる（「국」「미」「미국」）ため。
  これらの判定は ko 0.74〜0.99 で、おおむね正しかった。
- 韓国語の話者による指示（「다시 들어 보세요」「말해보세요」）は `ko` と判定された。教材の構成上、「解説の言語」が
  日本語だけとは限らない。言語フィルタの使い方（指示も学習言語として再生される）に関わる。

### 4.2 英語-ヒンディー語（hindi）

| 種類 | turbo | large-v3 | 例（抜粋） |
| --- | --- | --- | --- |
| ヒンディー語を `en` と判定し、ローマ字で書いた（辞書にない語が半分以上の `en` チャンク。概数） | 約 80（83 件のうち 1 秒未満 58 件） | 約 75（77 件のうち 1 秒未満 45 件） | 「Atais」（अट्ठाईस）、「Pachis」、「Chobis」、「Deh raha hoon」 |
| ヒンディー語を英単語に聞き間違えた（上の件数に含まれないもの） | 多数（未集計） | 未集計 | 「Peace」「Beasts」（बीस）、「These」（तीस）、「Pentes」（पैंतीस） |
| `hi` と判定されたのに、平滑化で `en` になってローマ字で書いた | 一部 | 約 15 | 「Kya aap kar sakt…」「Mein nahin kar s…」 |
| ヒンディー語の指示を英語に訳して書いた | 0 | 2 | 「सुनिए और दोहराइए」→「Listen and repeat」 |
| 幻覚 | 1 | 0 | 0.7 秒のチャンクに「уж kann sie…」（ロシア語とドイツ語の混ざった文） |
| 文字体系の確認が効いた | 1 | 0 | `en` と判定 → デーヴァナーガリーが出た → `hi` を採用（「जी नहीं」） |

- 文字体系の確認では、「英語と判定して英語の文字（ローマ字）で書いた」誤りは捉えられない。英語もローマ字の
  ヒンディー語もラテン文字だからである。
- 「Namaste」は、ヒンディー語を指定して認識してもローマ字のまま出る。

### 4.3 追加の実験: ローマ字で書かれた `en` チャンクをヒンディー語で認識し直す

turbo の `en` チャンクのうち、辞書（macOS の `/usr/share/dict/words`）にない語が半分以上の 83 件を、`hi` を指定して
認識し直した（99.7 秒）。

- **73 件（88%）がデーヴァナーガリーで書けた**: 「Atais」→「अट्ठाईस」系、「Beasts」→「बीस」、「Deh raha hoon」→「दे रहा हूं」、
  「Mereliye?」→「मेरे लिये?」など。
- 残る 10 件は「Namaste …」「DGA」など。ラテン文字のまま、または判断できないもの。

「英語の語彙として不自然なテキストは、もう一方の言語で認識し直す」という確認（文字体系の確認の延長）は、
en-hi に効果が大きい見込みがある。ただし単語のリストが必要で、Linux には macOS の辞書がない。依存（単語の頻度の
リストなど）を足すか、別の手段にするかの判断が要る（§7）。

  hindi で 1 秒未満の `en` の行。

## 6. 実際の教材で見えた問題と、パラメータの提案

| 問題 | 観察 | 提案 |
| --- | --- | --- |
| 平滑化の逆効果 | 交互に並ぶ教材では、前後がもう一方の言語のことが多い。hindi では変更の大半が誤った方向だった | `smoothing.low_conf = 0.0`（対象を 1 秒未満のチャンクに限る）と `neighbor_weight = 0.25` を既定にする。記録で試算すると、変わる件数は turbo の hindi で 11 → 3、large-v3 の hindi で 16 → 0 になる。レビューの結果で最終的に決める |
| 短い応答・単語 | korean はほぼ正しい。hindi の短い語は `en` に偏る（確率 1.0 のことも多い） | en-hi では、§4.3 の語彙の確認での認識し直しを検討する。言語判定だけ turbo にする（`[model] detect = "large-v3-turbo"`）設定も比べる価値がある（未計測） |
| 英語の説明の中の発音例 | hindi のナレーターの文の中のヒンディー語（「Namaste Rajni Ji」など）は `en` のローマ字になる。1 つのチャンクに 2 言語が混ざる | チャンク単位の判定の限界。M3 の言語フィルタでは「混在」の扱いを決める必要がある（表示上は `en` のまま） |
| ナレーターの繰り返し・指示 | 同じ文の繰り返しは正しく判定された。学習言語の話者による指示（「말해보세요」「सुनिए और दोहराइए」）がある | 言語フィルタで指示も学習言語として再生される。仕様の判断が必要（lead / ui） |
| 無音の長さ | 学習者が答えるための 3〜4.5 秒の間が多い。発話の間の 10% 点は約 200ms | `vad.merge_gap_ms = 100` は維持する（言語の混ざったチャンクを作らないため）。中国語の問答のように 200ms 前後の切り替わりもあるので、文単位の整形の `chunking.split_gap_ms` を 700 → 400ms に下げることを提案する（候補チャンクの言語判定には影響しない） |
| チャンクの長さ | 最長 4.9 秒で、`max_ms`（15 秒）に達するものはなかった。korean の 51%、hindi の 36% が 1 秒未満 | Pimsleur の短い単位はそのまま学習単位として使える。`chunking.min_ms = 1000` のつなぎ方は、間が 400ms 以内の同じ言語に限るので、3 秒の間をまたいではつながらない（妥当） |
| 文字体系の確認の誤検出 | 「Tシャツ」のラテン文字で不一致になった | 修正済み（`47a31da`） |
| 平滑化で null になったチャンクの認識の言語 | 前後に引かれた言語で認識し、カタカナで書いた | 修正済み（`47a31da`）。平滑化の前の判定の言語で認識する |
| 幻覚 | 1,123 チャンク × 2 モデルで 1 件だけ | 現状の捨て方（圧縮率・無音の確率）で十分に少ない。`too-dense` の印が有効だった |
| 処理時間 | 30 分の教材が 14〜20 分（M3 Pro） | 前半の改善案（エンコーダの出力の再利用、短いチャンクをまとめて認識）は、短いチャンクの多い Pimsleur で効果が大きい |

## 7. 判断が必要なこと

1. en-hi の語彙の確認（§4.3）を実装するか。する場合の単語のリストの入手方法（新しい依存。例: 単語の頻度のリストの
   パッケージ）。
2. 平滑化の既定値の変更（§6）。人間のレビューの結果を待つか、先に「短いチャンクだけ」にするか。
3. ヒンディー語のコースの既定のモデル（判定は turbo が自信を持って当てる文が多く、large-v3 は短い語に強い）。
4. 学習言語の話者による指示、発音例を含むチャンクの、言語フィルタでの扱い（仕様）。
