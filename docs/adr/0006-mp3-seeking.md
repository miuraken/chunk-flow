# 0006. MP3 のシーク精度の対策（ヘッダを隠して IndexSeeker を使わせる）

- 状態: 承認済み
- 日付: 2026-10-14
- 決めた人: lead（スパイク S2 の結果をもとに）
- 根拠: [docs/spikes/S2-playback.md](../spikes/S2-playback.md) §3（エミュレータでの計測。シークの誤差は出力のタイミングに依存しない測り方）
- 関係する節: 設計書 §7.2.2、§12（MP3 のシーク誤差）、§7.3.1、§7.4.6

## 背景

§7.2.2 と §12 は、MP3（特に VBR）のシーク誤差を S2 で検証し、対策を (a) MP4 への詰め替え、(b) M4A（AAC）への変換、(c) 自前の索引 から選ぶ、としていた。
S2 の結果（Media3 1.11.1）:

| ファイル | 既定（`FLAG_ENABLE_INDEX_SEEKING` の有無で同じ） |
| --- | --- |
| CBR（Info ヘッダ） | シーク後の誤差が位置に比例して変わる（10 分で −18〜+13ms） |
| CBR（ヘッダなし） | +13.1ms で一定 |
| VBR + Xing（TOC あり。LAME の一般的な出力） | **−158〜+2,474ms**（TOC による概算） |
| VBR（ヘッダなし） | **長さを 120 秒と誤認**（真値 600 秒）し、シークが破綻 |

`FLAG_ENABLE_INDEX_SEEKING` は「VBR ヘッダはあるが TOC がない」か「CBR とみなしたがファイル長が不明」のときにしか使われず、上の 3 種のどれも改善しなかった。

## 決定

1. **すべての MP3 を、読み出し時にヘッダを隠す DataSource（S2 の試作 `IndexSeekDataSource` 相当）を通して再生し、`Mp3Extractor` の
   `FLAG_ENABLE_INDEX_SEEKING` と組み合わせる。** DataSource は次の 2 つだけを行う。ファイルは書き換えない（SHA-256 も Drive の `sha256Checksum` も変わらない）。
   1. 先頭フレームの `Xing` / `Info` / `VBRI` の識別子を 0 で隠す（CBR とみなさせる）。
   2. `open()` でファイル長を `C.LENGTH_UNSET` として返す（長さが不明なので IndexSeeker が使われる）。
   - S2 では 3 種（VBR + Xing、ヘッダのない VBR、CBR）とも、先頭から再生したときとシーク後の誤差が**同じ一定の値**になった
     （ヘッダのあったファイルは +39.2ms、ヘッダのないファイルは +13.1ms）。
   - CBR も対象にする（既定では位置に比例してずれるため。全 MP3 で時間軸のずれを一定値だけにする）。
   - 実装は `core:playback`（ExoPlayer の `MediaSource.Factory`）。解析（`core:media`）も同じ DataSource を通して読む（ADR 0005）。
2. **MP3 の長さは、取り込み時の解析（デコード）で求めて `media_item.duration_ms`（`AudioItem.durationMs`）に使う。**
   上の DataSource を通すと ExoPlayer の長さは `C.TIME_UNSET`（不明）になるため。解析が終わるまでの長さは、取り込み時のメタデータ
   （`MediaMetadataRetriever` など）の値を仮に使い、解析の完了で置き換える。`PlaybackStatus.durationMs` も DB の値を使う。
3. **副作用: 遠い位置への最初のシークが遅い**（そこまでファイルを読み、索引を作るため）。S2 では 10 分の VBR で最初の遠いシーク（576 秒）が 1,182ms、
   以後は 30〜90ms。60 分の教材ではさらに遅くなる見込み（実機で要確認）。対策の候補:
   - (i) 開いた直後に、再生を妨げない優先度で末尾までの読み出し（索引の作成）を先に行う（ExoPlayer の先読みとは別に。実装方法は M1 で検討）。
   - (ii) シークが遅い間は UI に読み込み中を出す（バッファリングの表示で足りる見込み）。
   - (iii) 実機で問題になる場合だけ、解析のデコードで全フレームのバイト位置を記録し、それを使う自前の `SeekMap`（(c) 案）に進む。

## 採らなかった案（§12 の (a)(b)(c)）

| 案 | 採らない理由 |
| --- | --- |
| (a) 再エンコードせずに MP4 へ詰め替える | 詰め替えた MP4 は正確にシークできた（+13.1ms 一定）が、端末では作れない。プラットフォームの `MediaMuxer` は `audio/mpeg` のトラックを受け付けず（`IllegalStateException`）、Media3 の `Mp4Muxer` も MP3 に対応していない。自前の MP4 ライタが必要になり割に合わない。保存するファイルが元と変わる（SHA-256 と別に管理が必要）点も不利 |
| (b) M4A（AAC）に変換する（Media3 Transformer） | 再エンコードで音質が落ち、時間と電池を使い、ファイルも変わる。依存（Transformer）が増える。S2 では試していない |
| (c) 自前の時刻 → バイト位置の索引と `SeekMap` | 最初の遠いシークも速くなるが、Extractor / SeekMap の実装量が大きい（ギャップレス、ID3 など）。上の決定で精度は足りるので、最初のシークの遅さが実機で問題になった場合の次の手段として残す |

## 影響・リスク

- **Media3 の内部の挙動（ヘッダの扱い、IndexSeeker）に依存する**。Media3 を上げるときは、S2 の計測（`--es run seekfix`）で誤差が一定のままかを確かめる。
- ヘッダを隠したファイルでは、ヘッダのフレーム（1,152 サンプル）が無音として再生され、ギャップレスの情報（LAME のエンコーダ遅延）も使われない。
  そのため時間軸は「真の時刻 +（1 フレームのサンプル数 + エンコーダ遅延）」になる（LAME の MPEG-1 で +1,728 サンプル = 44.1kHz で +39.2ms、MPEG-2 / 2.5 で +1,152 サンプル = 22.05kHz で +52.2ms。S3 の D6 で実測）。
  解析も同じ DataSource で読めば解析と再生は一致する（D6 で確認。`MediaExtractorCompat(ExtractorsFactory, DataSource.Factory)` は Media3 1.11.1 にある。`@UnstableApi`）が、
  **PC ツール（ffmpeg）の時間軸との差が変わる**（ADR 0008）。
- 先頭の無音（ヘッダのフレーム）は 26ms（44.1kHz）〜 26ms（22.05kHz、576 サンプル）程度で、聞いてわかる影響はない見込み。
